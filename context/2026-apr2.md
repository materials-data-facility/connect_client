## MDF Connect v2: A Rebuilt Backend and a New Command-Line Client

In parallel with the Spotlight and dataset-curation work above, the MDF team rebuilt the core publishing infrastructure that researchers actually touch. The two pieces are a new backend (MDF Connect v2) and a new command-line client (`mdf`). Together they replace a stack of services and a Python client that had grown over almost a decade and were beginning to limit what we could ship next. The motivation was not novelty. The old system worked, but adding new behavior to it had become painful: every change touched several services, the metadata schema was a nested triple of `dc/mdf/custom` blocks that nobody outside the team could remember, and the client surface area had drifted away from how researchers describe what they want to do. Rebuilding gave us a chance to remove that friction before adding the LLM-driven features described in the next reporting period.

This work also speaks to **section 37 (impact on the discipline)** and **section 41 (infrastructure)**: the v2 backend is the substrate that supports the OMol25 Spotlight, the in-flight 100 TB / 50 TB / 1 PB landmark datasets, and the upcoming metadata-extraction pipeline.

### The v2 backend

MDF Connect v2 is a single FastAPI application that runs on AWS Lambda behind an HTTP API Gateway, deployed via SAM. It is one codebase, one deployment, and one set of routes. The whole API surface is defined under `cs/aws/v2/app/routers/` and covers submissions, streams, files, previews, search, dataset cards, citations, curation, and admin statistics. Pydantic v2 models validate every request and response, so the contract between client and server is explicit and machine-readable.

The metadata schema is the part most likely to matter to other groups looking at MDF as a template. The old format buried fields under `dc.titles[0].title` and similar nested paths inherited from DataCite. The new `DatasetMetadata` model is flat: `title`, `authors`, `description`, `keywords`, `data_sources`, `organization`, `ml`, `extensions`, and a small set of optional fields like `license`, `funding`, `related_works`, `methods`, `facility`, `fields_of_science`, and `geo_locations`. Translation to DataCite for DOI minting happens server-side in `to_datacite()`. v1 payloads still flow in from older tools, and `migrate_v1_payload()` converts them transparently, so the schema change did not break any prior contributor. ML metadata in particular is now a first-class object (`MLMetadata` with `data_format`, `task_type`, `splits`, `keys`) rather than an opaque blob hidden under `projects.foundry`. It is searchable and it shows up in dataset cards.

Storage is abstracted behind a `StorageBackend` interface with two implementations: a local filesystem backend for development and a Globus HTTPS backend for production that talks directly to the NCSA endpoint at `data.materialsdatafacility.org`. The same applies to the database layer, which has a SQLite implementation for local work and a DynamoDB implementation in production with two global secondary indexes (by user and by organization) to keep listings cheap. This is the kind of plumbing that does not show up in screenshots but is the reason a graduate student can spin up the entire MDF stack on a laptop in two terminals and develop against it without an AWS account or a Globus client. We have used that capability ourselves throughout the year and it has noticeably shortened the loop between idea and working prototype.

The submission lifecycle is now a state machine that we can describe in one diagram. A dataset enters as `pending_curation`, can be `withdrawn` by the submitter, `rejected` with a reason, edited, `resubmitted`, then `approved` and `published`. Each transition is recorded in a `curation_history` field on the record itself. Editing metadata on a published dataset auto-creates a minor version bump (1.0 to 1.1), inherits the existing DOI, and updates the DataCite record and the search index. Curators can soft-delete with a reason. SES email notifications fire when a dataset enters the queue, when it is published, and when it is rejected, with the rejection email carrying the curator's feedback verbatim. None of this required a new service. It is all in the same FastAPI app.

Public endpoints exist for the parts of the dataset that should not need authentication. `GET /preview/{source_id}` returns the dataset's profile (file listing, formats, column summaries for tabular files, structure for JSON, sampled rows for the first table). `GET /citation/{source_id}` returns the citation in BibTeX, RIS, APA, and DataCite XML. `GET /stats/{source_id}` returns view and download counts. `GET /card/{source_id}` and `GET /detail/{slug}` return the compact dataset card and, when the caller is authenticated, an inline `permissions` object so a frontend can show or hide action buttons without a second round-trip. The frontend slug parser handles both UUID-style and human-readable source IDs (`levine_abo2179_database_v2.1-1.0`), which sounds trivial but eliminates a recurring class of bug where a dataset's URL would not resolve because the slug regex was too strict.

The rest of the hardening is the unglamorous list that turns a prototype into something we are willing to put external users on top of. Per-actor rate limits and request-body caps run as middleware. Every request gets an `X-Request-Id` and a structured completion log. Storage backends reject path traversal. Async jobs (profile generation, publish, embedding generation) go through SQS with a dead-letter queue after three retries. CORS handles the credentialed and wildcard cases correctly. The CloudFormation template retains the DynamoDB tables on stack delete so a fat-fingered teardown cannot lose data. The submissions list supports filtering by status and an `include_counts=true` flag that returns per-status counts in the same response, which is what the curation dashboard actually wanted.

### The command-line client

The new client is a single Python package, `mdf-agent`, that ships a CLI called `mdf`. The visible surface is eleven commands. That is a deliberate choice. The old client exposed dozens of functions and the average researcher only ever used three of them. The new help screen fits on one terminal page:

- `mdf publish` to submit a dataset, either from a directory or a manifest
- `mdf search`, `mdf show`, `mdf list`, `mdf related`, `mdf versions` to find and read
- `mdf status`, `mdf watch` to follow a submission through curation
- `mdf cite`, `mdf open`, `mdf preview`, `mdf clone` for everything you do once a dataset is live
- `mdf approve`, `mdf reject`, `mdf pending` for curators
- `mdf login`, `mdf whoami`, `mdf doctor`, `mdf setup` for auth and diagnostics
- `mdf config`, `mdf admin`, `mdf dataset` as namespaced sub-apps for power users

A few specific choices are worth calling out because they change how the tool gets used. First, `mdf publish ./data/ --title "..." --author "..." --submit` works as a one-liner. There is no required manifest file, no project scaffolding, no "first set up your account" detour. If a researcher prefers a manifest, `mdf manifest init` creates an `mdf.yaml`, `mdf manifest discover *.csv` extracts metadata from files into it (PDF, CSV, Excel, JSON, YAML extractors are registered), and `mdf publish --submit` reads it. Both paths produce the same flat v2 payload that the backend validates.

Second, every command that produces structured output has a `--json` flag that emits a clean JSON envelope with no ANSI codes. This is what makes the CLI usable from CI pipelines, notebooks, and LLM agents without screen-scraping. `mdf status my_dataset_v1 --json | jq .submission.status` is the canonical example. We have already used this in our own demo scripts and in the autonomous-lab streaming demo.

Third, `mdf watch` polls the submission until it reaches a terminal state and renders progress as a small status timeline (`pending_curation` → `approved` → `published`, with the DOI when it appears). This is the moment most researchers care about, and the old flow asked them to refresh a web page or run `status` in a loop. Watching it move feels different.

Fourth, auth resolution has a documented order: explicit token, environment variable, confidential client credentials (`MDF_CLIENT_ID` + `MDF_CLIENT_SECRET`), dev mode, and finally interactive Globus OAuth. The confidential client path is the one CI pipelines need, and it works without a browser. HTTP requests retry on 429 (respecting `Retry-After`), 502, 503, 504, and connection errors. File uploads retry too. None of this is novel, but it is the kind of behavior that a tool either has or does not, and the old client did not.

The CLI is also the surface we expose to LLM agents. The `mdf_agent.skill` package contains a `skill.md` and a set of handlers (`scan_folder`, `create_manifest`, `suggest_mappings`, `validate_and_preview`, `publish`) that an LLM can call directly to drive a publishing session. We have run this end-to-end against the local backend and it produces the same payloads the human-driven flow does. This is the seed of the agent work that the next reporting period builds on.

### Streaming ingest for automated labs

A separate set of endpoints (`/stream/create`, `/stream/{id}/upload`, `/stream/{id}/upload-url`, `/stream/{id}/append`, `/stream/{id}/snapshot`, `/stream/{id}/close`) handles the case where a dataset is not a static directory but a stream of files arriving from an instrument or simulation. A lab can `mdf stream create --title "Lab 42 XRD Run"`, push files in as they are produced, snapshot to a dataset at any point, and close the stream with `--mint-doi` when the run is over. Files can come in as base64 in the request body for small payloads or via a presigned URL for anything larger. We added a progress bar for uploads over 6 MB because the prior silence on a slow Globus link made researchers nervous.

The dataset profiler runs after each stream snapshot and after any submission whose `data_sources` contain `stream://` URIs. It reads up to 10 MB of each file, detects the format (CSV, TSV, JSON, HDF5, CIF, PNG, JPEG, text, binary), and produces a `DatasetProfile` with column summaries for tabular data, structure for JSON, sample lines for text, and format-specific extras like CIF formula or image dimensions. The profile is stored as JSON on the submission record and surfaces in the public preview endpoints. This is what makes a freshly uploaded dataset useful to a stranger within seconds of arrival, instead of requiring them to download the bundle and inspect it themselves.

### Semantic search and dataset relationships

We added two discovery features that did not exist in MDF before. `mdf search "battery cathodes" --semantic` runs a vector search over OpenAI `text-embedding-3-small` embeddings of each dataset's title and description. Embeddings are generated automatically when a dataset is published (an async job; if the OpenAI call fails the publish still succeeds and the next rebuild fills the gap). A periodic snapshot packs every vector into a content-hashed binary blob in S3, with a `current.json` pointer that gets atomically swapped. The search endpoint scans the in-memory matrix and the same snapshot can be served to the browser for client-side scanning. Query embedding happens server-side via `POST /embed` so the OpenAI key never reaches the frontend.

`mdf related my_dataset_v1` returns datasets that share authors (ORCID-matched first, name-matched as a fallback). `mdf related my_dataset_v1 --by similar` returns nearest neighbors over the embedding snapshot, which is what the dataset detail page's "you might also like" widget shows. Neither of these shipped in prior MDF phases, and both have already changed how we click around our own data when looking for examples.

### Cross-publishing from external repositories

The `mdf import` command (added this period) cross-publishes a dataset that already lives on Zenodo (or, via an adapter pattern in `mdf_agent/importers/`, any future external repository) into MDF without forcing the contributor to re-upload anything. We fetch the public metadata, mirror or link the files according to the contributor's choice, and produce an MDF record that points at the source DOI. This is a small piece of code, but it removes an objection we have heard for years, that contributing to MDF means duplicating data the contributor already published somewhere. It does not, anymore.

### What this means for researchers

The point of all of the above is to make the act of publishing, finding, and reusing materials data take less time and require less ceremony. A researcher with a folder of XRD patterns can now go from local disk to a published, DOI-bearing, citable dataset in three commands and a curator's approval. A lab running automated experiments can stream files in as they are produced and ship them as a dataset on the way out the door. A reviewer reading a paper that cites an MDF dataset can hit the URL, see a preview of every file, sample the first table, and download a BibTeX entry without logging in. A curator can see what is in the queue, read the metadata, approve or reject with notes, and have the submitter notified by email automatically. None of these flows existed in this shape a year ago, and we have already used all of them in production for the OMol25 release and in staging for the upcoming landmark datasets.

The work also has implications for **section 38 (impact on other disciplines)**. The architectural pattern (flat Pydantic schema, FastAPI app on Lambda, abstract storage and store layers, a small CLI on top) is portable. Several groups have asked us about reusing it. We are happy to share, and the code is already open under the `materials-data-facility` GitHub organization.

### Future directions

Most of the next-period work falls out naturally from the foundation described above. Now that submission, curation, search, and preview are all REST endpoints with typed payloads, an LLM agent can drive any of them. The metadata extraction pipeline we are co-developing with the Global Observatory project already produces the flat v2 schema, and we expect to wire it into `mdf import` and `mdf publish` as a `--auto-extract` mode that reads PDFs, supplementary files, and instrument metadata and proposes a draft manifest the user only has to approve. The semantic search snapshot becomes the basis for cross-dataset retrieval inside future MDF assistants. The streaming endpoints are the right place to add real-time alerting and provenance capture for autonomous labs. And the dataset profiler will grow to handle the formats we keep seeing in the landmark datasets (large HDF5 hierarchies, multi-resolution microscopy stacks, simulation trajectory files) so that a 100 TB dataset is as easy to peek at as a 100 MB one. The tools are no longer in the way of the science, which is what we wanted.
