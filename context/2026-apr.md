**24. What were the major goals and objectives of this project?**

In this phase of the project, one major goal has been to make MDF easier to use from the places where researchers already work: local folders, analysis scripts, instrument workflows, notebooks, and automated laboratory systems. The new MDF Agent command line client and MDF Connect v2 backend directly support that goal. They reduce the amount of MDF-specific knowledge needed to publish a dataset, make metadata creation and validation more approachable, and create a clearer route from raw research files to a citable, searchable, reusable dataset.

This work also supports the Phase IV goal of applying LLMs and related automation to common materials science tasks. The project has not treated AI as a replacement for researcher judgment. Instead, the current implementation uses structured metadata extraction, validation, and assistant-accessible tool handlers to help with the tedious first pass: scanning folders, identifying file structure, preparing manifests, checking submissions, and showing the user what will be published. The researcher still supplies the scientific meaning, authorship, context, and final approval.

**25. What was accomplished under these goals?**

## MDF Connect v2 Command Line Client and Backend Modernization

During this reporting period, the MDF team built much of the practical infrastructure needed to make publication, curation, discovery, and reuse of materials datasets easier for researchers. The most visible result is a new MDF Agent command line client, paired with a redesigned MDF Connect v2 backend. Together these components form a working path from a scientist's local files or laboratory stream to a validated MDF submission, a curator review queue, dataset preview pages, search results, citation exports, and DOI-aware publication records.

This is now a demonstrated software workflow, not only an architecture plan. A developer can start the v2 backend locally, submit a dataset, move it through curation, approve it, mint a mock DOI, retrieve a dataset card, create a stream, upload files, list stream contents, preview data, close the stream, and snapshot it into a dataset. That local-first design matters because it gives the team a way to test scientific workflows before deploying them into production infrastructure. It also gives collaborators a way to understand the service by running it, rather than only reading a diagram.

## MDF Agent CLI for Researcher Workflows

The MDF Agent client was built to remove a long-standing source of friction in scientific data publication: the gap between where data are produced and where they become usable public research objects. Materials researchers often have a directory of CSV files, simulation outputs, instrument metadata, notes, or a Globus-accessible data path, but the steps required to turn that material into a citable dataset can be hard to remember and easy to postpone. The new client gives users a direct workflow from the terminal. A researcher can authenticate with Globus, initialize an MDF manifest, discover metadata from files, validate the submission, publish to MDF Connect, check status, view a dataset card, retrieve citations, inspect version history, and search MDF from the same interface.

That changes who can reasonably publish data and when. A user no longer needs to understand the old nested submission structure or know which backend endpoint expects which payload. The client presents commands in the language of a data publication workflow: `mdf publish`, `mdf status`, `mdf search`, `mdf show`, `mdf versions`, `mdf cite`, and `mdf clone`. The lower-level API still exists for automation and testing, but the normal path now looks more like the way scientists already work.

The client supports two styles of publication. In the first, a user creates and edits a persistent `mdf.yaml` manifest. This is useful for datasets that will be revised, shared with collaborators, or kept under version control with the data. In the second, a user can publish directly from a local directory with command line flags for title, author, and submission behavior. The direct mode is intentionally short. It is meant for the many cases where the barrier is not a lack of scientific metadata but the overhead of starting the process. The manifest mode remains available when the dataset needs richer description, reuse metadata, or careful review before submission.

The CLI now includes a preflight and validation path that makes publication less opaque. Before a dataset is submitted, the client can summarize the local sources, count files and bytes, check basic metadata, and report issues. On publication, local files can be uploaded to MDF storage through Globus HTTPS, with streaming uploads, progress reporting, retries for transient failures, and a generated zip archive for directory downloads when the dataset size permits. Real research datasets are rarely a single clean file. They are directories, nested files, instrument outputs, and sometimes large collections that need stable paths. The new client handles that reality more directly than a form-only workflow.

## Metadata Extraction and AI-Assisted Preparation

Metadata extraction is a practical part of this design. The repository now includes extractors for tabular files, JSON and YAML files, and PDFs, with a registry that scans a folder and merges the extracted information. In the examples, CSV and JSON files are examined for column names, row counts, and schema structure. For a researcher with X-ray diffraction data, DFT outputs, or instrument configuration files, this means the client can produce a first draft of useful metadata instead of starting from an empty form. The output still needs human judgment, but the boring first pass can now be automated.

This same work creates a better platform for AI-assisted publication. The repository includes skill handlers that let an AI coding or research assistant scan a folder, create a manifest, suggest mappings from column names, validate and preview a submission, publish, create and update streams, and manage curation actions through the backend. This is a realistic use of LLMs in MDF because it is bounded by schema validation, backend checks, and visible artifacts. An assistant can help prepare the package, but the scientist still sees what will be submitted.

## Programmatic Access for Labs and Pipelines

The client was also designed for programmatic use. The `MDFAgent` high-level Python API and the lower-level `BackendClient` give notebooks, scripts, CI jobs, and other research software access to the same workflows. Authentication can be interactive through Globus, or it can use environment variables for confidential client credentials and preexisting tokens. Labs that publish from scheduled workflows, autonomous facilities, or data processing pipelines need that second path. A command line tool that works only for a person at a terminal helps individual users. A command line tool with a Python API and non-interactive authentication can become part of a lab's data infrastructure.

## MDF Connect v2 Backend Architecture

The backend work in `cs/aws/v2` is the other major accomplishment. The new backend is a FastAPI application deployed through AWS Lambda using Mangum, with development and production storage paths that reflect how the service is actually used. In development, it can run locally with SQLite and local filesystem storage. In production, the architecture is designed around DynamoDB for submissions and streams, Globus HTTPS storage for file access, AWS SAM for deployment, SQS-backed asynchronous jobs, DataCite for DOI minting, Globus OAuth for authentication, and Globus group membership for submitter and curator authorization. This gives the team a backend that can be tested locally without AWS while still matching the production shape closely enough to reduce surprises at deployment time.

The core dataset submission flow is now implemented in the v2 backend. A client submits a flat v2 metadata payload, the backend validates it with Pydantic, migrates legacy v1 `dc/mdf/custom` metadata when needed, generates a source identifier and version, writes the record to the store, and returns a versioned source ID. The new metadata schema uses researcher-facing field names such as title, authors, description, keywords, funding, related works, methods, facility, domains, data sources, license, and ML-specific metadata. DataCite translation happens later, when a DOI is minted. This is a cleaner model than making every user or client construct DataCite-shaped metadata from the beginning.

## Versioning, Curation, and DOI-Aware Publication

Versioning is now built into the system. The backend can list versions, resolve the latest version, mark older records as no longer latest, show version history, and compute version diffs. Published metadata edits create minor version bumps rather than silently overwriting the public record. Later versions can mint version-specific DOIs while preserving the dataset DOI as the conceptual object. Scientific datasets are rarely static in practice. Files get corrected, descriptions improve, authors add related works, and machine-learning metadata becomes clearer after a dataset has been used. The v2 backend gives MDF a way to represent that evolution without losing citation clarity.

Curation has also been rebuilt as an API-driven workflow. The backend provides endpoints to list pending submissions, inspect curation details, approve a submission, reject it with a reason and suggestions, withdraw a submission, resubmit after revision, and soft-delete when needed. Curator authorization is tied to user IDs or Globus groups, with development settings that allow local testing. The approval path can trigger DOI minting and publication, while rejection records feedback in the submission history. This is a concrete improvement for both sides of the MDF publication process. Submitters can see what happened and what to fix. Curators get a structured queue rather than an informal review trail.

## File Storage, Previews, and Dataset Profiles

The backend includes a practical file and preview layer. Stream files can be uploaded through the API for small files or through a direct upload URL for larger files. The storage abstraction supports local development and production storage backends, with file metadata including names, sizes, paths, checksums, content types, storage timestamps, and download URLs. Preview endpoints can summarize streams and datasets, list files, return file-level previews, and produce samples.

The dataset profiler scans stored files and creates a compact profile with total files, total bytes, file formats, tabular columns, row counts, sample rows, JSON structure, text previews, and basic information for other file types. This directly supports discoverability because a user should not have to download a large dataset just to decide whether it contains the kind of data they need.

## Streaming Data from Instruments and Automated Labs

Streaming data support is one of the clearest new capabilities. The backend can create a stream, append file batches or file counts, upload stream files, list files, close a stream, mint a DOI for a completed stream when requested, and snapshot a stream into a dataset submission. The client exposes this through `mdf stream create`, `mdf stream upload`, `mdf stream status`, `mdf stream files`, `mdf stream snapshot`, and `mdf stream close`. A local Argonne XRD and TGA demonstration shows the intended workflow: create a stream for an experimental run, append XRD patterns, append TGA files, inspect the accumulated stream status, close the stream, and snapshot the run into a dataset record. This moves MDF closer to the way automated laboratories and instruments actually produce data.

The significance of streaming is practical, not abstract. A traditional publication workflow often begins after an experiment has ended and someone has organized the files. That delay is one reason datasets are lost, under-described, or published without enough context. With the v2 streaming model, data can be recorded as it is produced, along with lab identifiers, sample identifiers, run IDs, instrument names, timestamps, and operator metadata. A stream can remain open during a campaign and later become a citable dataset. This supports research environments where data collection is continuous, where multiple instruments contribute to the same sample record, or where autonomous systems need to publish outputs without waiting for a manual packaging step.

## Search, Citations, Cloning, and Reuse

Search and discovery were also advanced. The backend exposes a search endpoint that can search published datasets and streams, with filters for year, organization, author, keyword, and domain. The response shape includes result metadata and facets so a frontend can support the common search pattern of querying, filtering, and refining. Dataset card endpoints return compact summaries with titles, authors, descriptions, keywords, organization, status, DOI links, statistics, data sources, ML metadata, and profile summaries. Citation endpoints provide formats such as BibTeX, RIS, APA, and DataCite.

The repository also includes the foundation for semantic search. The backend can generate embeddings from dataset title, keywords, and description using OpenAI's `text-embedding-3-small`, store embedding metadata, rebuild coverage through curator-only admin endpoints, and publish an embedding snapshot for similarity search. The client exposes semantic search and related-dataset commands, including related-by-author and nearest-neighbor lookup over embeddings. This work is early compared with the mature publication path, but it is already enough to demonstrate a different kind of discovery. A user can search for conceptual similarity, not only exact keywords. For materials data, where the same idea may appear under several names or where a dataset description may not use the user's preferred terms, this is a useful direction.

The client and backend together also support cloning and reuse. A researcher can inspect a dataset, retrieve citation information, preview files, and clone stream or dataset files locally. The clone path validates trusted Globus HTTPS hosts before using tokens, supports file filtering, and downloads with authorization when needed. This makes MDF more useful after publication. A dataset that can be found but not easily pulled into a working directory is still too far from analysis. The new workflow shortens the path from discovery to reuse.

## Demonstrated Behavior, Tests, and Hardening

Several demonstrations and tests show that these capabilities are not only design notes. The repository includes a 90-second CLI demo, walkthroughs for human-driven and agent-assisted publication, a full local backend workflow demo, and local lab streaming demos. The test suite covers metadata extraction, client endpoint calls, auth resolution, backend routing, publication flow, curation transitions, pagination, rate limits, request size limits, path validation, upload confirmation, stream file access control, version ordering, local storage path traversal protection, and DataCite-related behavior. The tests are especially important for the backend because this service touches authentication, storage, DOI state, public metadata, and user-owned files. A failure in any of those areas would not be cosmetic.

The architecture also includes operational hardening that will matter as MDF Connect v2 moves further into production use. API Gateway throttles, Lambda reserved concurrency, request size limits, rate limits, CloudWatch log retention, SQS async worker settings, and environment-specific deployment parameters are represented in the SAM template. The application can run with mock DataCite and local authentication in development, then switch to production Globus authentication, DataCite credentials, and real storage settings. User bearer tokens are not persisted into SQS or SQLite job payloads for transfer initiation; those jobs are run inline so tokens stay in request memory. File path checks reject traversal and prevent a user from confirming or downloading a file path that does not belong to the stream. These details are not glamorous, but they are the difference between a prototype and a service that can responsibly handle research data.

The current work is well past the stage of a sketch, even though it is still moving toward the final MDF publication system. The CLI has a coherent user model. The backend has a real API contract. The storage and curation layers exist. Dataset and stream records can be created, inspected, versioned, and published. Search, cards, citations, previews, and semantic-search hooks are in place. The code contains tests for common failures and security-sensitive edges. The important point for this reporting period is that the team has built and demonstrated a more practical MDF workflow, one that meets researchers closer to where their data are produced and carries that data farther toward reuse.

**30. Technologies or techniques**

The major technology output from this period is a modernized MDF publication stack with two connected components: the MDF Agent CLI/SDK and the MDF Connect v2 backend. The CLI provides researcher-facing commands for manifest creation, metadata discovery, validation, publication, status checks, search, citations, cloning, configuration, and streaming. The SDK exposes the same capabilities to Python scripts, notebooks, CI jobs, and lab automation.

The service can run locally with SQLite and local storage, while the production architecture uses AWS Lambda, DynamoDB, SQS, Globus HTTPS storage, Globus OAuth, Globus group authorization, and DataCite.

**37. What was the impact on the development of the principal discipline(s) of the project?**

For materials science, this work makes MDF better suited to the current scale and style of research data. Modern materials datasets may be large, generated continuously, produced by autonomous labs, or intended for machine-learning reuse. They need more than a static landing page. They need streaming ingestion, rich metadata, previewable structure, stable identifiers, version history, DOI-aware citation, and search that works across both text and data context.

The user-facing benefit is that MDF becomes less like a separate publication chore and more like a working part of the research process. A graduate student can publish a small XRD dataset from a local folder. A lab can stream files from an instrument campaign and snapshot the result into a citable dataset. A curator can review submissions through structured endpoints. A frontend can show dataset cards, previews, search facets, citations, and version histories without rebuilding backend logic. A machine-learning researcher can search for datasets with ML-ready metadata, inspect formats and sample rows, and decide whether the data are useful before downloading everything. Each of these is a small reduction in friction. Together they make data publication and reuse more likely.

**38. What was the impact on other disciplines?**

Although MDF is focused on materials science, the architecture developed here is broadly relevant to other data-intensive fields. Chemistry, physics, biology, engineering, and facility science groups face the same problem: valuable data are produced faster than people can package and describe them. The MDF Connect v2 architecture is a concrete example of how a domain data facility can combine command line tools, cloud services, authentication, curation, versioning, DOI workflows, previews, and AI-adjacent metadata support without making the system feel like a black box.

The streaming model is especially relevant outside materials science. Any field with instruments, sensors, autonomous experiments, or repeated simulation campaigns can benefit from a pattern in which data are recorded as they are produced, tracked with run metadata, and later promoted into a citable dataset. The same approach could be adapted for beamline data, chemistry automation, environmental monitoring, biological imaging, and other domains where the dataset begins as a stream rather than a finished folder.

The examples developed for MDF Agent and MDF Connect v2 can be adapted into teaching material because they show the full route from raw files to a published, searchable dataset. This is particularly useful for teaching modern materials informatics, where the boundary between data collection, data management, and machine-learning reuse is becoming much thinner.
